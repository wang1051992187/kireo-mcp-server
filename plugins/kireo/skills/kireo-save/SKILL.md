# kireo-save

## 第 0 步：定位项目

先调用 `project_info` 工具，把它返回的 `key` 和 `source` 原样告诉用户 —— 项目认错了是用户唯一能当场发现的错误，藏起来用户就再也发现不了了。

如果用户这句话里附带了备注（比如"记一下这次为什么这么改"），把它当作本次提炼的额外线索；没有就按整段会话处理 —— 这里没有参数占位符，直接理解用户这句话里说了什么。

这个宿主不会替你把工具输出自动塞进这段正文，第一步（定位项目、读既有条目）要靠你自己主动调用对应工具去跑，不要假设结果已经在上下文里。

## 提炼规则

你要把刚刚这段会话提炼成结构化的上下文条目。分三步，不要跳步。

## 第一步：抽取（宁多勿少）
先不加判断地列出所有候选。

## 第二步：过滤（两道测试，都要过）
1. **6 个月后测试**：未来的我能否在 60 秒内从这个仓库重新读出来？
   能 → 丢弃。那是代码索引的活，不是记忆的活。
2. **证据测试**：能否指出会话里的具体依据（文件路径、跑过的命令、
   用户说过的原话）？不能 → 丢弃。

## 第三步：归并
读一遍 context_load 给你的既有条目。对每条新条目判断：
- 它推翻了哪条既有条目？→ 填进 supersedes
- 它跟某条既有条目说的是同一件事？→ 直接跳过，不要写

## 输出约束
- content 60–400 字符。约束不会因为写得长而更准。
- evidence 必填非空。**编不出依据就不要写这条。**
- 拿不准的宁可归到 open（未完成/待确认），不要归到 decision。

## 分类体系

# 六类 context bucket：判据与正反例

每类给三条正例、三条反例。反例覆盖两类最常见的失效模式：把讨论/猜测当成
结论写下来，以及把 60 秒内能从仓库读出来的东西也存成记忆。

## decision — 定了什么、为什么、否决了什么

✅ 「用 BullMQ 而不是 Redis Streams 做 embedding 队列，因为需要延迟队列和
   重试语义；Redis Streams 的 consumer group 要自己实现重试。」
✅ 「代码索引定为 Pro-only，free 档只给记忆 —— 见 plan-config.ts free
   namespaces:3，一个项目两个桶就到顶。」
✅ 「档位改造跟功能一起做，不放到下游：BETA_UNLIMITED 一关 free 就回到
   30 天 TTL，代码索引会被静默扫走。」

❌ 「我们讨论了 BullMQ 和 Redis Streams。」
   ← 讨论不是决策。把讨论写成决策是本功能最危险的失效模式：注入一条
     不存在的约束，比没有上下文更糟。没定就归到 open。
❌ 「决定用 TypeScript。」
   ← 从 package.json 一眼可见，60 秒内能从仓库读出来 → 丢弃。
❌ 「用户说这个方案不错。」
   ← 没有可引用的依据，evidence 写不出来 → 丢弃。

## constraint — 硬性限制、不可违反的边界值

✅ 「free 档 namespace 上限是 3 个，一个项目里 ctx 桶 + code 桶就占两个 ——
   见 plan-config.ts free.namespaces:3。」
✅ 「MEMORY_LIMITS.CONTENT_MAX 是 8000，但 context 卡片自己又叠了一层更紧
   的 60–400 字符上限 —— 写卡片按后者算，不是按 8000 算。」
✅ 「不能改 LanceDB 表 schema：getMemoriesTable() 对已存在的表直接
   openTable 不校验 schema，生产是单机换镜像，一旦加列全站写入停摆。」

❌ 「这个函数有一些边界情况要注意。」
   ← 没写出具体是哪个边界、数值是多少，事后没法核对，等于没写。
❌ 「namespace 长度好像有个上限。」
   ← "好像"就是没验证过。constraint 卡的是已确认的硬限制，不是猜测；
     猜测应该走 open，不能冒充 constraint。
❌ 「测试超时时间是 10 秒。」
   ← vitest.config.ts 里一行就能看到，60 秒内能读出来 → 丢弃。

## gotcha — 踩过的坑、已经证伪的错误认知

✅ 「namespace 的 slug 段上限其实是 15，不是最初以为的 20 —— repoSlug 自身
   有 27 字符内部预算，见 slug.ts:6；已经按 15 实现并过了幂等断言。」
✅ 「`claude mcp add ... -- npx -y -p @kireo/mcp-server kireo-mcp` 会报
   `unknown option '--env'`：短参数 `-p` 被 claude 自己的解析器吞掉了，
   必须用长参数 `--package=`。」
✅ 「`/v1/memories/batch` 失败字段是 `failures`，不是 `failed` —— 一开始
   看名字直觉猜错了，改的时候 rest/types.ts、run-index.ts、service.ts
   三处都要对上。」

❌ 「这个 bug 挺难查的。」
   ← 没说清楚错在哪、正确认知是什么，下次遇到同样的坑还是会踩。
❌ 「测试挂了，改了一下就好了。」
   ← "改了一下"不是证据，看不出改的是什么、为什么之前是错的。
❌ 「TypeScript 报错，加了个 any 就过了。」
   ← 这是在掩盖问题，不是记录教训；记下来只会诱导下次继续用 any。

## open — 还没定、还没做完、需要确认

✅ 「代码索引要不要支持批量删除原语，还没定 —— 现在只有逐条删，量大的
   仓库会很慢，Plan 3 再看。」
✅ 「`resume --all`（跨项目续读 kireo-home）还没实现，CLI 的
   KNOWN_COMMANDS 已经预留了但 handler 会直接报错退出。」
✅ 「要不要在看板加"盲审"流程来测漏报，还没跟产品确认 —— 现在的
   采纳/不采纳只能测出误报，测不出漏报。」

❌ 「后面再优化一下性能。」
   ← 优化哪里、优化到什么程度都没有，六个月后的自己一样看不懂要做什么。
❌ 「这个方案可能有问题。」
   ← 具体是什么问题、依据是什么都没说。open 一样需要证据，只是允许
     结论未定，不是允许信口开河。
❌ 「TODO: 完善这里。」
   ← 代码里的 TODO 注释本身就在仓库里，60 秒内能读到，不需要占记忆的
     位置。

## map — 东西在哪、怎么找

✅ 「`SearchHit` 类型定义在 apps/api/src/search/service.ts:67，
   packages/shared 里没有这个类型，别去 shared 找。」
✅ 「context 相关的落地代码在 packages/mcp-server/src/context/ 下：
   transcript.ts 解析会话、outbox.ts 管本地缓冲、project.ts 解析项目
   身份、score.ts 算权重、render.ts 渲染、verify.ts 校证据。」
✅ 「MEMORY_LIMITS 和 PLAN_CONFIG 两份基线常量都在 packages/shared/src/
   plan-config.ts，17-35 行。」

❌ 「代码结构还挺清楚的。」
   ← 没有指出具体路径，等于什么都没说。
❌ 「工具都在 tools 目录里。」
   ← 熟悉这类项目结构的人扫一眼目录树就知道，60 秒读仓库能得到，
     不值得占用记忆。
❌ 「相关逻辑大概在 context 那一块。」
   ← "大概"说明连自己都没确认路径，不能当作可复用的地图。

## pref — 团队/用户认准的风格与工作方式

✅ 「commit message 用 brief 里给的原文，不要自己改写、不要翻译。」
✅ 「遇到需要架构判断的、或者读了一堆文件还是没进展的，直接停下来报
   BLOCKED，不要硬着头皮做完 —— 做砸了比不做更糟。」
✅ 「测试文件必须能过 `tsc --noEmit`；提交前自己跑一遍
   `pnpm -F <包名> typecheck`，不要等 CI 帮忙发现。」

❌ 「大家都喜欢简洁的代码。」
   ← 空洞的场面话，落不到任何一次具体的写法选择上，没法指导下一次
     怎么写。
❌ 「用户人挺好的。」
   ← 跟怎么干活毫无关系，占用的是记忆的位置，不是有效的偏好。
❌ 「尽量写好一点的代码。」
   ← 没有具体到"好"是哪一条标准（命名？分层？测试覆盖？），无法执行。

## 保存
每条候选都通过了上面两道测试后，调用 `context_save`：
- `host`: `"codex"`（固定值，照抄，不要改成别的宿主名）
- `session_id`：当前会话的标识（拿不到稳定值就用一个本次运行内保持不变的字符串）
- `entries`：通过测试的候选，字段照 schema 来（bucket / content / evidence / files / importance / supersedes）
- `uncertain_indexes`：自评拿不准的条目下标（从 0 开始）。证据是转述而不是原文、或者你不确定「讨论过」和「定下来了」的区别，就把它列进去 —— 标成不确定永远比说错要好，resume 那边会渲染成 `[uncertain]`。
- `transcript_path`（可选）：本次会话 jsonl 的绝对路径，知道就传。工具会拿它做字面证据校验：evidence 里引的文件路径/命令在会话里找不到的，自动补进不确定集合。
- 第一次在这台机器上调用会被工具强制预览：它只返回脱敏后的正文，不写盘也不上传。
  把那段正文原样展示给用户，确认没有业务机密混进去，再带 `dry_run: false` 调用一次即可真正保存。
  之后不再强制 —— 想再预览就显式传 `dry_run: true`。
把返回结果里存了几条、跳过了几条，原样回显给用户。
